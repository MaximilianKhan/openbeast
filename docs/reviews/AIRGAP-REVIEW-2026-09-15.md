### 1. OFFLINE=true conf key + egress kill switch with bounded timeouts
`serving-models` · **top-tier** · airgap 9/10 · feasibility 8/10 · days

**Problem.** Nothing in the stack can be told 'there is no internet'. The result is not a clean refusal but long stalls followed by wrong diagnoses: ~11 minutes inside cmake for the Web UI fetch, minutes of git connect timeouts ending in 'local changes in llama.cpp/?', a hf traceback where a friendly die() was intended.

**Proposal.** One conf key (joining WEIGHT_ENFORCE, FAST_BOOT et al in openbeast.conf.example) that every network-touching site consults. Concretely: ob_cmake_flags() appends -DLLAMA_USE_PREBUILT_UI=OFF (kills the build-time HF fetch dead); update.sh gains --rebuild-only and takes it implicitly under OFFLINE, skipping the line 61 fetch and the line 72-74 pulls and going straight to the rebuild, with an honest message; bootstrap.sh prints 'place <file> at <path> and re-run' instead of calling hf download; compose gains OFFLINE_MODE=true, ENABLE_VERSION_UPDATE_CHECK=false, HF_HUB_OFFLINE=1; and every remaining outbound command is wrapped so it fails in seconds rather than minutes (`timeout 20`, git's GIT_HTTP_LOW_SPEED_LIMIT/TIME, HF_HUB_ETAG_TIMEOUT, pip --retries 0). Exporting HF_HUB_OFFLINE=1 for the whole stack turns every stray huggingface_hub call into an immediate OfflineModeIsEnabled instead of a stall.

**Replaces.** the current implicit assumption of connectivity in bootstrap.sh, scripts/update.sh, scripts/lib/hardware.sh and docker-compose.yml

**OSS component.** none needed — huggingface_hub's HF_HUB_OFFLINE, git's low-speed timeouts and Open WebUI's OFFLINE_MODE are all existing upstream switches we simply never set

**First step.** Add OFFLINE to scripts/lib/conf.sh using the existing two-line idiom (copy line 76's FAST_BOOT pattern: `OFFLINE="${OPENBEAST_OFFLINE:-$(_ob_conf_value OFFLINE || echo false)}"; export OFFLINE`) plus a commented `#OFFLINE=false` in openbeast.conf.example, then make it do exactly two things in the first PR: (1) guard bootstrap.sh:350 behind an import probe like agent.sh:21 already uses, and under OFFLINE=true replace it with a die() naming the wheels/weights to pre-stage — this is the only true hard blocker; (2) append `-DLLAMA_USE_PREBUILT_UI=OFF` in ob_cmake_flags (scripts/lib/hardware.sh:252) so both bootstrap and update inherit it, killing the 660s build-time HF fetch. Leave compose and the timeout wrappers for a follow-up.

**Ranker's reasoning.** Verified against code, not taken on trust — and unusually, every claim in the proposal checked out exactly.

NOT COVERED. No OFFLINE / HF_HUB_OFFLINE / OFFLINE_MODE / ENABLE_VERSION_UPDATE_CHECK exists anywhere in OpenBeast's own code (the sole hit is HF_HUB_DISABLE_TELEMETRY in a vendored example, llamacpp-clean/examples/llama-eval/llama-eval.py:42). openbeast.conf.example carries ~39 keys, none of them this. docs/ has no offline install or update procedure (only docs/EGRESS_PRIVACY.md, which is about HIDING egress via a Tailscale exit node — the opposite problem). docs/TODO.md:1127 "Air-gapped bundle (M/L)" is the complementary half (weights+images+wheels tarball, i.e. getting bits IN), not this (behaving correctly with no egress) — and crucially that bundle is unusable until this exists, because the install still dies before it can use the bundle. beast-lang covers documentation corpora, not installer/updater egress. So this is genuinely unclaimed ground and it is the substrate two already-planned items sit on.

WHY TOP-TIER RATHER THAN MERELY NICE. bootstrap.sh:350 runs `pip install --user -q -U "huggingface_hub" -r agents/requirements.txt` unconditionally, under `set -euo pipefail` (line 20). The `-U` on an unpinned name forces a PyPI index query, so this line fails even on a box where every wheel is already installed and every weight is already on disk. The only supported installer therefore CANNOT run to completion in a closed network — that is a possibility change for the paved road, not a polish item. agent.sh:21 already demonstrates the correct guard (`if ! python3 -c "import openai"`); bootstrap simply never got it.

THE STALL AND MISDIAGNOSIS CLAIMS ARE REAL AND ANCHORED. (a) The ~11 minutes is arithmetically exact, not rhetorical: llama.cpp/scripts/ui-assets.cmake:422 `TIMEOUT 300` for dist.tar.gz plus :433 `TIMEOUT 30` for its sha256, looped over two candidates (`${version}`, then `latest`) = 660s, with LLAMA_USE_PREBUILT_UI defaulting ON at llama.cpp/CMakeLists.txt:138, re-attempted on every rebuild where LLAMA_BUILD_NUMBER has moved (the stamp skip only fires on an exact version match). (b) scripts/update.sh:72-74 swallows the first `git pull`'s stderr with `2>/dev/null`, runs a SECOND full-connect-timeout pull, then dies with "local changes in llama.cpp/? stash or reset them" — minutes of stall ending in a diagnosis that names the wrong cause, in a script an operator reaches for precisely when confused. (c) bootstrap.sh:383 calls `$HF_BIN download` raw, so an offline operator gets a huggingface_hub retry traceback where the file's own die()/friendly-guidance idiom was clearly intended.

I CHECKED THE PROPOSED FIX FOR SELF-HARM, which is where this kind of proposal usually dies. Turning off the prebuilt UI does NOT break the build offline: ui-assets.cmake:526-537 falls through to `message(WARNING)`, not FATAL_ERROR, and upstream even prints disconnected-environment guidance there. The only loss is llama-server's own embedded UI at :8080, which OpenBeast never uses — the frontend is Open WebUI on :3000, and no repo doc points a user at the built-in one. Cost is genuinely zero here.

HONEST LIMITS, and they matter for scoring. This is an install/update/rebuild capability, not an inference capability. An already-installed rig serves fine offline today: start.sh never pulls, digest-pinned images already present locally don't contact a registry, serve scripts read local GGUFs, and the agent's egress is already bounded (agents/tools.py:1468 fetch timeout=30, :1540 search timeout=15). So this does not rescue a running stack — it rescues bootstrap, update.sh --llama, and every rebuild. The compose third is the weakest: ENABLE_VERSION_UPDATE_CHECK=false suppresses a non-blocking frontend ping to GitHub (degrade, not break), and the digest-pinned open-webui image already bakes its embedding model in, so OFFLINE_MODE is belt-and-braces rather than a fix. I would ship the compose stanza but not sell it. One design constraint the proposal understates: exporting HF_HUB_OFFLINE=1 stack-wide also makes bootstrap's legitimate weight download impossible, so OFFLINE must never default true and the "place <file> at <path>" message becomes load-bearing rather than cosmetic.

NOISE-FLOOR CHECK — this is not one of the repo's inside-the-noise features. There is no scored claim to deflate: the effect is deterministic (a fetch either runs or does not) and unit-testable without a network in tests/test_scripts.sh — assert ob_cmake_flags emits -DLLAMA_USE_PREBUILT_UI=OFF under OFFLINE=true, and assert update_llama takes the rebuild-only path. Feasibility 8 rather than 10 because the conf-key plumbing is a two-line idiom (conf.sh:76/136) and ob_cmake_flags is one case statement, but the fan-out across bootstrap.sh, update.sh, compose, docs and the conf-key tests makes the proposal's "days" estimate right rather than optimistic. Sequence it so the two possibility-changing lines (bootstrap pip guard, cmake flag) land first and the timeout wrappers follow — if the PR is shipped as one lump, the cheap high-value half gets held hostage by the cosmetic half.

### 2. FETCH_ALLOW_HOSTS — an exact host:port allowlist for offline knowledge servers
`knowledge-beyond-lang` · **worth-doing** · airgap 8/10 · feasibility 9/10 · hours

**Problem.** agents/tools.py:1324-1330 refuses every private/loopback address for everyone, and the sole escape hatch is OPENBEAST_FETCH_ALLOW_TAILNET for CGNAT 100.64.0.0/10. A closed-network doc mirror on 10.x, or kiwix-serve on 127.0.0.1, cannot be opened by the model's reader tool at all. This blocks every other feature in this list.

**Proposal.** An operator-config allowlist of EXACT host:port entries (not ranges, never model-supplied), checked before the private-range refusal. Must be applied in BOTH copies of the check — `_fetch_url_blocked` (:1357) and `_vet_addr` as reached from `_pinned_open` (:1406) — because the connect-time copy is authoritative and will otherwise refuse the pin even after the friendly check passes. Wire through scripts/lib/conf.sh:138 exactly like FETCH_ALLOW_TAILNET, document in docs/REFERENCE.md:43, and add the mirror-image test to tests/test_fetch_guards.py alongside the existing CGNAT cases. Security posture is preserved and arguably improved: an exact host:port list is tighter than the existing whole-/10 flag.

**Replaces.** The OPENBEAST_FETCH_ALLOW_TAILNET single-range special case (it becomes one entry in the general mechanism).

**OSS component.** none — stdlib

**First step.** In agents/tools.py, put the allowlist check inside the single choke point `_resolve_vetted` (:1333) — NOT in both callers as proposed — parsing OPENBEAST_FETCH_ALLOW_HOSTS at call time into a normalized set of (host_lower, port) pairs, where port is mandatory (scheme default filled in) and entries with CIDR/wildcards are ignored with a loud reason; on a hit, skip the private/loopback refusal for that (host, port) only, leave resolve-and-pin untouched, and add the mirror-image cases next to TestTailnetCGNAT in tests/test_fetch_guards.py:209.

**Ranker's reasoning.** VERIFIED, NOT COVERED. agents/tools.py:1314-1331 is exactly as described: `_vet_addr` special-cases only Tailscale CGNAT 100.64.0.0/10 + fd7a:115c:a1e0::/48 behind OPENBEAST_FETCH_ALLOW_TAILNET, then refuses every loopback/private/link-local/reserved address with no operator escape. conf.sh:138-140 wires only that flag, docs/REFERENCE.md:43 documents only it, openbeast.conf.example:179 exposes only it, tests/test_fetch_guards.py:209 pins only the CGNAT policy. grep for ALLOW_HOSTS/allow_hosts across .py/.sh/.md: nothing. docs/TODO.md's only adjacent item is "Air-gapped bundle (M/L)" (:1127), an offline INSTALLER (weights/images/wheels), not a fetch policy. docs/BEAST_LANG_PLAN.md is explicitly "not a web fetcher at agent time" (:325) — filesystem packs — so it neither covers nor conflicts.

WHY IT IS NOT NOISE — it closes a currently-shipped inconsistency. docs/TOOLS.md:57 and the tools.py:1290-1294 comment state `web_search` DELIBERATELY bypasses this guard because SEARXNG_URL may legitimately be loopback/tailnet. So in a closed network a local SearXNG over an intranet index already returns hits, and then `fetch` of any hit (10.x doc mirror, 127.0.0.1 kiwix-serve, internal Gitea/Confluence/devdocs) is refused at resolve time with "non-public address 10.x.y.z". Search works; reading the result is impossible. That is binary capability, not an effect size. It is NOT top-tier because the failure mode today is honest (an explicit refusal string the model sees — no hang, no silent empty page) and the stack still boots and serves air-gapped without it: this unlocks a class of offline knowledge sources rather than making closed-network deployment possible.

ONE CORRECTION, IN THE PROPOSAL'S FAVOR. "Must be applied in BOTH copies — `_fetch_url_blocked` (:1357) and `_vet_addr` as reached from `_pinned_open` (:1406)" is a misdiagnosis. Both entry points funnel through one function: `_fetch_url_blocked` calls `_resolve_vetted` at :1371, `_pinned_open` at :1411, and `_vet_addr` is only ever reached from `_resolve_vetted`:1350. A single insertion in `_resolve_vetted` covers the friendly check, the connect-time pin, and the redirect handler (:1433). Also `_vet_addr(addr: str)` receives neither host nor port, so it is the wrong layer for a host:port rule regardless — `_resolve_vetted` already has (host, port, scheme). Hours, one file plus conf/docs/test, stdlib only.

SECURITY CAVEAT THE PROPOSAL OVERSTATES. "Tighter than the whole /10" holds only for IP:port entries. A NAME:port entry is weaker than it looks: the allowlist suppresses the range refusal for that name, so whoever answers internal DNS for `docs.internal` can point it at 169.254.169.254 or the rig's own :8443/:8444 — the exact hazard docs/TOOLS.md:157 names — and the pin faithfully dials it. Keep the pin, prefer IP:port in docs and the conf example, and make the port mandatory or `10.0.0.5` silently opens every port on that host.

SECOND CAVEAT. `fetch` is a GUEST-role tool (docs/TOOLS.md:142-143), so a process-wide env allowlist hands the intranet mirror to guests too. Acceptable, but state it in REFERENCE.md rather than discovering it later.

REPLACES claim is sound: FETCH_ALLOW_TAILNET collapses into one range-shaped entry — but keep the old key as an alias so Max's live tailnet config does not break.

### 3. Offline bundle: build on a connected box, install from USB
`install-bootstrap` · **top-tier** · airgap 10/10 · feasibility 7/10 · days

**Problem.** Four fetches on the install path are fatal and have no local alternative: llama.cpp source (bootstrap.sh:312), PyPI wheels (bootstrap.sh:350), the 20 GB GGUF (bootstrap.sh:383), and the two digest-pinned container images (bootstrap.sh:418-422). There is no bundle format and no --from-bundle flag.

**Proposal.** `scripts/bundle.sh --build <outdir>` on a connected box emits: llama.cpp source tarball at the pinned revision; `docker save` of both @sha256-pinned images straight out of docker-compose.yml (reuse bootstrap.sh's existing `grep -E '^\s+image:'` extraction at line 422 so the bundle and compose can never drift); a wheelhouse from `pip download -r agents/requirements.txt huggingface_hub`; the GGUF named in scripts/weights.registry; a repo tarball; and BUNDLE.manifest — sha256 + bytes + filename per artifact, in the same tab-separated shape weights.registry already uses, so verify-weights.sh's proven parser generalizes. Then `./bootstrap.sh --from-bundle /mnt/usb/openbeast-bundle`: verify the manifest FIRST, refuse on any mismatch, then `pip install --no-index --find-links=<dir>/wheels`, `docker load -i`, build llama.cpp from the local tarball, and place+hash-verify the weight. This is docs/TODO.md:1127 made concrete, plus the two artifacts that line omits — the llama.cpp source and the manifest itself.

**Replaces.** The four fatal fetches in bootstrap.sh (lines 312, 350, 383, 418-422)

**OSS component.** pip download / --find-links and docker save|load are the whole mechanism; no new dependency. `oras` or `skopeo copy --dest-dir` if OCI-layout images are preferred over docker save tarballs.

**First step.** Land the enumeration refactor with zero behavior change, before any tarballing: move the two artifact-identifying snippets bootstrap.sh already owns — the compose-image extraction at bootstrap.sh:418-422 (`grep -E '^\s+image:' docker-compose.yml | awk '{print $2}'`) and the default-weight resolution + registry sha256 lookup at bootstrap.sh:369-377 (`WEIGHT_FILE`/`HF_REPO` + the `awk -F'\t' '$3==f'` against scripts/weights.registry) — into `scripts/lib/bundle.sh` as `ob_bundle_images()` and `ob_bundle_weight()`, and have bootstrap.sh source and call them. That makes one list of what a bundle must contain that both `--build` and `--from-bundle` read, kills the drift risk by construction, and is a pure read/refactor that can land while the GPU measurement finishes.

**Ranker's reasoning.** Verified every anchor. bootstrap.sh:312 (`[[ -d llama.cpp/.git ]] || git clone --depth 1 https://github.com/ggml-org/llama.cpp.git`) under `set -euo pipefail` — clone fails, compound fails, script dies. bootstrap.sh:350 (`python3 -m pip install --user -U huggingface_hub -r agents/requirements.txt`) — same, fatal. bootstrap.sh:383 (`hf download`) → `die "download failed"`. Only the images are milder than the proposal claims: 418-422 `warn`s on pull failure, so the box boots headless and the real failure surfaces later at start.sh:633 ("frontend containers failed to start") — feature loss, not boot loss. Three of four are genuinely fatal, which is enough: on a closed network a fresh install cannot reach step 3.

Not covered and not planned in any actionable sense. docs/TODO.md:1127 is a single wishlist bullet ("Air-gapped bundle (M/L). Offline installer: weights + images + wheels + repo tarball with checksums") with no plan doc, no flag, no script — `grep -rn 'from-bundle|bundle.sh|wheelhouse|docker save|--no-index|find-links'` across the repo returns nothing but that line and two README "fork it, air-gap it" marketing mentions. bootstrap.sh's flag parser (lines 29-35) has exactly `--no-start`, `--minimal`, `--preflight`. The proposal also adds the two things line 1127 omits and that are the actual reproducibility teeth: the llama.cpp source at a pinned revision, and BUNDLE.manifest.

The design choices are right for this repo rather than generic. Reusing the compose `image:` grep is not cosmetic — it is the only reason a bundle can't ship a different image than compose runs, which is the same failure the comment above line 418 already warns about for moving tags. Reusing weights.registry's tab-separated shape means verify-weights.sh's parser and doctor's size check generalize instead of a second format appearing. Verify-manifest-FIRST-then-install is the correct ordering given the box has no network to re-fetch a bad artifact from.

Honest limits, none disqualifying: (1) the wheelhouse is the fragile part — `pip download` yields platform+ABI-specific wheels, so a bundle built on the Arch reference box installs on a matching CPython minor and glibc and nowhere else; the manifest must record python tag and platform and `--from-bundle` must refuse on mismatch rather than fall through to a source build that needs a compiler and network. (2) The bundle covers four fetch classes, not five: bootstrap only *checks* the heavy system deps (driver, CUDA, cmake, gcc, Docker), so the closed box still needs a distro mirror for those — the honest claim is "no internet during OpenBeast install", not "no repository of any kind". (3) Only the default weight travels; the other ~20 registry rows stay manual. (4) The stated dependency is real — with `--depth 1` and no revision, two bundles a week apart ship different engines, and the llama.cpp pin has to land first or the manifest hash is meaningless.

top-tier is earned on the strict test: this is not "nicer". Every other air-gap finding — offline docs, disabled web_search, local skill index — is downstream of a stack that exists on the box. Today there is no path from a cloned repo to a serving rig without egress, and this is the one feature that creates it. Size is days as claimed, and it is days of shell plumbing with no new dependency.

### 4. Offline bundle: scripts/bundle.sh export|import + bootstrap.sh --offline
`serving-models` · **top-tier** · airgap 9/10 · feasibility 7/10 · weeks

**Problem.** All four of bootstrap's acquisition stages are network-only and there is no first-install path without internet: llama.cpp source (bootstrap.sh:312), Python wheels (bootstrap.sh:350), the 20 GB default weight (bootstrap.sh:383), and the two digest-pinned images (bootstrap.sh:420). Plus the build-time Web UI tarball nobody knows about.

**Proposal.** One command on a connected box produces a single verified tarball; one command on the closed-network box consumes it, and `bootstrap.sh --offline` runs the existing steps against it instead of the network. Contents, each mapping to a named break: (1) a `git bundle` of llama.cpp carrying BOTH the pinned SHA and the LLAMACPP_WATCH.md rollback SHA, cloned full-history not --depth 1, which is what makes the documented pin-back possible offline; (2) llama.cpp's prebuilt UI dist.tar.gz staged into llama.cpp/tools/ui/dist so ui-assets.cmake takes its priority-1 path and never reaches for Hugging Face; (3) `pip download` of agents/requirements.txt + huggingface_hub, installed with `pip install --no-index --find-links`; (4) `docker save` of both digest-pinned refs, imported with `docker load`; (5) every weights.registry row plus a sha256 manifest for the non-weight parts. Import verifies before it writes, and refuses on any mismatch.

**Replaces.** bootstrap.sh's git clone / pip install / hf download / docker pull stages, and the undocumented manual assembly an operator would otherwise have to reverse-engineer

**OSS component.** git bundle; docker save/load (or zot / registry:2 for a standing in-network mirror); pip download + pip install --no-index --find-links

**First step.** Ship the Web UI half alone, in an hour, as its own PR — it is independently valuable and fixes a live silent misbehavior: stage llama.cpp's release `dist.tar.gz` into `llama.cpp/tools/ui/dist/` (the priority-1 branch at `llama.cpp/scripts/ui-assets.cmake`, `if(EXISTS "${SRC_DIST_DIR}/index.html")`) and add `-DLLAMA_USE_PREBUILT_UI=OFF` to `ob_cmake_flags()` in `scripts/lib/hardware.sh` when `--offline` is set. That single cmake option converts today's two-attempt 300s-timeout HF stall plus a `message(WARNING)` plus a UI-less `llama-server` into a build that simply works. Do this before writing any of `bundle.sh` — it proves the one item an operator hand-assembling files would never discover.

**Ranker's reasoning.** **Verified, not taken on faith.** All four cited line numbers are exact: `bootstrap.sh:312` `git clone --depth 1`, `:350` `pip install --user -U`, `:383` `hf download`, `:420` `docker pull` over the two digest-pinned refs in `docker-compose.yml`. There is no `--offline` flag — `bootstrap.sh:26-31` parses only `--minimal`, and `--minimal` still runs stages 2/3/4. No offline install path exists anywhere in `docs/INSTALL.md`, `UPDATING.md`, or `doctor.sh`. Meanwhile `README.md:217` and `:703` both sell "air-gap it" as a feature. The marketing is ahead of the code by four network calls.

**Not already covered, but be honest about the overlap.** `docs/TODO.md:1127` carries "**Air-gapped bundle (M/L).** Offline installer: weights + images + wheels + repo tarball with checksums" — a one-line roadmap wish, unbuilt, no plan doc. So this is a *known* gap, not a discovered one, which normally costs a proposal its novelty. It survives because it adds the two items the TODO line misses, and those are the two that actually bite.

**The find that justifies the whole thing.** `llama.cpp/scripts/ui-assets.cmake` provisions the Web UI in three priorities. `llama.cpp/CMakeLists.txt:137-138` sets `LLAMA_BUILD_UI=OFF` and `LLAMA_USE_PREBUILT_UI=ON` by default, and `ob_cmake_flags()` overrides neither — so OpenBeast's build takes priority 3, `hf_download()`, every time. Offline that is `file(DOWNLOAD ... TIMEOUT 300)` against `huggingface.co/buckets/ggml-org/llama-ui`, twice (the resolved `b<N>` version, then `latest`), for two files each: **~10 minutes of dead stall inside `cmake --build`**, then `message(WARNING)` — not `FATAL_ERROR` — and `emit_files()` emits a **zero-asset table**. bootstrap reports success, `llama-server` starts, and `:8080` serves no UI. Upstream's own fallback text admits the fix ("In a disconnected environment, download the pre-built UI... extract to `tools/ui/dist`"), which means nobody who hand-assembles an offline install will find it unless they read a cmake script. The proposal's item (2) lands exactly on `SRC_DIST_DIR`. Correctly targeted.

**Second real find.** `docs/LLAMACPP_WATCH.md:136-144` documents the rollback pin as `git -C llama.cpp fetch --depth 1 origin 86a9c79f8` — a **network fetch**. On a closed box the documented recovery from a bad llama.cpp upgrade does not exist. Item (1) is right that a bundle is what restores it, and it is cheap: I confirmed Max's tree is **not** shallow (`is-shallow-repository` → false, `.git` = 420 MB) and that `86a9c79f8` is present as a commit object. So both SHAs bundle today for 420 MB.

**Three corrections the plan needs.**
1. **"Every `weights.registry` row" is 470.2 GB across 55 rows.** That is not a tarball. Default must be the one 20 GB `bootstrap` weight, with opt-in extras by alias. And "verify before it writes" at 20 GB means ~40 GB free — needs streaming verify or split volumes, not a naive two-copy dance.
2. **`git bundle create` from a shallow source is the trap.** `bootstrap.sh:312` creates `--depth 1` clones, so on any export box that was itself bootstrapped, `--all` yields a bundle that cannot serve the rollback SHA. `bundle.sh export` must assert `git rev-parse --is-shallow-repository` is false and `fetch --unshallow` first, or it silently ships the broken half of item (1).
3. **`pip download` is ABI-bound, not portable.** The 10 pins in `agents/requirements.txt` resolve to wheels for one CPython minor + manylinux tag; `--no-index --find-links` on a target box with a different Python fails hard, and `--break-system-packages` (`bootstrap.sh:342-347`) is already in play. Export must take `--python-version`/`--platform` explicitly and the manifest must record them.

**Scope, stated plainly.** This fixes *install*, not *runtime*. It does not touch `scripts/setup-tailscale.sh` (`login.tailscale.com` — the tailnet control plane is cloud-coordinated by design; headscale is the OSS answer), `setup-sandlock.sh`'s GitHub clone, opencode, or Open WebUI container egress. Those are separate findings. But install is the gate: none of them matter if the box cannot be built in the first place.

**Why top-tier anyway, under a skeptical bar.** The repo's noise-floor habit is about features whose *measured effect* is indistinguishable from zero. This one has no measurement problem — the outcome is binary and observable in an afternoon: cable unplugged, does `bootstrap.sh --offline` produce a serving stack. Today the answer is no, and one of the four failures is silent. "weeks" is overstated; `git bundle`, `docker save/load`, `pip download`, a staged tarball and a sha256 manifest are five boring well-worn mechanisms plus an `--offline` flag threaded through four stages. Days, not weeks — hence feasibility 7, docked for the wheel-ABI edge and the 20 GB verify. Value 9 rather than 10 only because a determined operator *could* hand-carry the files; the proposal's own REPLACES clause concedes this. But they would hit the UI trap, and they could never roll llama.cpp back.

### 5. OPENBEAST_AIRGAP — one switch, resolved in conf.sh, that reshapes the runtime instead of leaving it lying
`agents-skills-webui` · **worth-doing** · airgap 7/10 · feasibility 8/10 · days

**Problem.** There is no offline mode. Every finding above is a separate component behaving as if the internet exists; an operator on a closed network has no single thing to set and no way to make the stack tell the truth about itself.

**Proposal.** A tri-state (`auto|0|1`) resolved once in scripts/lib/conf.sh and exported to every surface. ### 11. Local PKI for the published surfaces

**Problem.** HTTPS on 443/8443/8444/8445/8446 is Let's Encrypt via the coordination server. In this mode `tailscale serve --http=` (no cert) or a direct tailnet-IP bind sits behind the proxy.

**Replaces.** `tailscale serve --https` + Let's Encrypt cert provisioning

**OSS component.** step-ca (smallstep/certificates) with ACME; Caddy as the terminating proxy

**First step.** Add a cert-expiry check to scripts/doctor.sh beside the existing informational serve block (doctor.sh:342-399): for each FQDN in `tailscale serve status`, read notAfter from tailscaled's cert store (/var/lib/tailscale/certs/<fqdn>.crt, falling back to `tailscale cert --cert-file -`), WARN under 21 days, FAIL when expired or when the file is absent while `--https` mappings exist, and make the fix hint name renewal-needs-internet plus the local-CA path — then fix the same omission in the 000 branch of scripts/client.sh:250-252 so "TLS failed" lists expired cert ahead of clock skew. Hours, zero new daemons, and it converts today's silent misdiagnosis into a named failure before any step-ca work is committed to.

**Ranker's reasoning.** VERIFIED NOT COVERED. `grep -rn "tailscale cert"` → zero hits outside llamacpp-clean. No cert/expiry check exists in scripts/doctor.sh (its only TLS-adjacent code is informational: doctor.sh:342-399 prints `tailscale serve status` mappings) or scripts/healthcheck.sh. The proposal is the missing other half of the headscale path, not an alternative to it.

THE FAILURE IS REAL AND BINARY, not noise-floor. Five surfaces are published only as `--https` (setup-tailscale.sh:178, 192/196, 205, 220/224, 239, 257). Clients hardcode the scheme: scripts/setup-client.sh:306-307 build `https://$HOST_FQDN:8443/v1` and `:8444/api/slot` unconditionally, and rig auto-detection at :295-301 walks `tailscale status --json` peers. Worse for provisioning: there is no supported way to point a client at a plain-HTTP rig at all — the https:// scheme is not a flag — so the "just fall back to LAN" answer requires hand-editing generated env files.

WHY NOT TOP-TIER. (1) Single-box closed-network works today: BIND_HOST defaults to 127.0.0.1 (lib/conf.sh:56) and nothing in the boot path touches a CA. Certs only matter once a second device exists. (2) The hard offline blocker on the remote-access pillar is the coordination plane, not the cert — an offline `tailscaled` cannot enroll a new node regardless of who signs the cert. PKI alone buys you nothing without headscale or a LAN bind; paired with either, it is mandatory. (3) A loud degraded path exists (BIND_HOST=0.0.0.0, warned at lib/conf.sh:60 as "the ENTIRE stack network-reachable without auth"). So this restores authenticated, browser-grade transport rather than making boot possible.

TWO THINGS THE PROPOSAL UNDERSTATES. (a) "Every in-process gate stays unchanged" is false for identity. `Tailscale-User-Login` IS the read gate on beast-chat (chat_server.py:947, 1029; conf.sh:185) and beast-artifact (artifact_server.py:106, 699, 742-770), and today only `tailscale serve` can inject it because the upstreams are loopback-bound. Put Caddy in front of those same loopback upstreams and a LAN caller sets that header itself — the read gate collapses. Caddy must strip it unconditionally and, in the no-tailnet case, mint it from something. That turns into the feature's real prize: step-ca issues CLIENT certs too, so Caddy mTLS CN → injected login header gives closed-network device identity with no IdP — the one thing the repo has no offline answer for. Say that in the plan or the gates silently weaken. (b) Plain HTTP over the tailnet is NOT a free substitute: chat_server.py:1114-1131 ships a PWA manifest and /icon.svg for "Add to Home Screen", and secure-context loss kills install/service-worker on a phone. That is the concrete reason to hold real TLS rather than drop to `--http=`.

SIZE HONESTY. "Days" holds for Caddy's internal CA on one surface. step-ca plus fleet trust distribution is the long tail: Linux update-ca-certificates and macOS `security add-trusted-cert` script, but iOS requires a manual profile install AND the hidden Settings→About→Certificate Trust "Enable Full Trust" toggle, which cannot be automated — and the phone is the beast-chat use case. Budget that as docs plus a `doctor` check, not code.

Scope note the proposal misses: `agent.sh:27` installs the same file too (guarded behind `import openai`, so only bites a fresh box) and `.github/workflows/ci.yml:31` also consumes it.

(B) The hash half is compliance, not connectivity. Weights are already sha256+size pinned (`scripts/weights.registry`) and container images digest-pinned — the genuinely deployment-deciding artifacts (GGUF acquisition, docker images, the llama.cpp build) are untouched by this. (3) Wheelhouse is ~35 wheels / tens of MB with an unanswered distribution question (committing it to a public Apache-2.0 repo is a choice, not a default). Still hours-to-a-day of mechanical work, so 8.

RECOMMENDATION: ship it, but **split it** — land the wheelhouse + `--no-index` path and the huggingface_hub pin as the air-gap change (that is the boot fix), and treat hashes + the pip-audit `--no-deps` removal as a separate supply-chain PR whose real justification is making SOC2_READINESS.md:111 stop lying. Do not let the compliance half gate the boot fix.
