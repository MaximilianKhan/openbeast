### [artifact] agents/artifact_server.py:632 — high (verifier: certain)
The D27 audit budget only covers *refused* requests, so the one route an unauthenticated caller may reach (`/api/artifacts/health`) writes an unbudgeted audit row carrying an attacker-sized, attacker-chosen `login` value — the same disk-fill primitive D27 was written to close, reopened at larger bytes-per-request.

**Verifier's correction:** Real, but restate it — the finder got the reachability right and the framing half-wrong, and the severity is medium, not high.

TWO separate gaps, both in `_record` (agents/artifact_server.py):

(1) NO BYTE CAP on the audited identity — agents/artifact_server.py:593. `entry["login"]` is the raw `Tailscale-User-Login` header, uncapped, while the raw path beside it IS capped at 128 chars (line 584). (2) NO BUDGET AT ALL on the one credential-free route — the health exemption at line 678 (`elif principal.login is None and request.url.path != HEALTH_PATH`) leaves `denied` empty, so line 602's condition is false and line 632-633 takes the un-budgeted `else: audit(entry)`. **Verifier's correction:** REAL MECHANISM, WRONG SEVERITY AND WRONG CONSEQUENCE. ### agents/artifact.py:1039
`remove()` skips `_require_owner` whenever `_read_meta` returns None — which includes a meta.json that is valid JSON but not an object — so the one irreversible mutation fails OPEN on exactly the corruption where the other three mutators fail closed.

**Why refuted:** The mechanism is described correctly (agents/artifact.py:1039-1041 does skip _require_owner when _read_meta returns None, which includes a valid-JSON non-object meta.json per the isinstance guard at :503), but it is not a defect.

(1) The finder counted three mutators and omitted the fourth. publish (agents/artifact.py:708-723) treats the identical non-dict meta as `new = meta is None`, builds a fresh record with "owner": resolved_owner and never calls _require_owner — i.e. a non-owner can TAKE OVER a corrupt-meta id, a strictly larger permission than deleting it, and that is documented deliberate behaviour (module docstring lines 36-40, D14/R4, test_publish_after_a_crashed_publish). The whole module treats a non-dict meta uniformly as "no record here": list_artifacts skips it (tests/test_artifact_store.py:325), get_meta returns None (:341), can_view returns False (artifact.py:1158-1159), publish claims the id, remove clears it. remove() is consistent with that doctrine, not an outlier; the other three mutators raise "no such artifact" as a consequence of the same no-record verdict, not as a deliberate ownership fail-closed.

(2) The precondition is unreachable through any code path and self-defeating as an attack. _write_meta (artifact.py:505-520) always json.dumps a dict into a mkstemp file and os.replaces it with an fsync'd parent, so no crash, kill or power cut can leave a bare-string meta.json (the crash test at tests/test_artifact_store.py:288-307 confirms the real crash shape is an ABSENT meta.json, which is the intended debris-cleanup path the finder concedes). Getting a non-object meta.json requires write access to <store>/<id>/meta.json inside a 0700 tree — and that party can already `rm -rf` the artifact. The only distinct remote principal (DELETE /api/artifacts/{id}, artifact_server.py:1141-1147, locality-token gated) has no API by which to corrupt meta.json. So the scenario needs two separate actors, one of whom does not need this bug at all.

(3) Two factual errors inflate the severity. "Nothing logs a refusal": the removal IS logged to index.jsonl with the caller's normalized login (artifact.py:1045-1047), so it is attributable, not silent. And the destroyed versions are already unreachable to everyone including the owner (can_view False, get_meta None, absent from the gallery) — dead data recoverable only by hand-editing meta.json from a shell, by the same party who corrupted it.

(4) The proposed fix regresses the module: refusing on an unreadable record makes that id unremovable via the server, the MCP tools and scripts/artifact.sh, while publish would still step over it — leaving shell `rm -rf` as the only cleanup on a store deliberately designed so operators never touch the disk. That is the D14-class wedge an earlier review round removed.

Severity claimed critical is wrong by at least three notches. The only accurate residual is a low-grade classification inconsistency inside _read_meta itself (unparseable JSON raises ArtifactError and so fails closed in remove, while non-object JSON returns None and does not) — a consistency nit, not a security hole, and not worth touching shipped code that has survived three hostile rounds.

### scripts/healthcheck.sh:252
The artifact restart kills the recorded pid with a bare `kill -0` liveness test and no /proc/<pid>/cmdline identity check, so a recycled pid in .run/artifact.pid is SIGTERM'd — and scripts/openbeast-watchdog.timer runs this path unattended every 5 minutes.

**Why refuted:** The code reads as the finder describes (scripts/healthcheck.sh:251-255 kills the recorded pid behind a bare `kill -0`, no /proc/<pid>/cmdline check, and scripts/openbeast-watchdog.service+.timer do run `healthcheck.sh --restart` unattended every 5 min with KillMode=process), but the failure scenario is not reachable, for three independent reasons.

1) The stale record cannot persist in the automated path. Line 260 rewrites .run/artifact.pid UNCONDITIONALLY on every failing tick, with the pid of the python launched two lines earlier — success or failure. So the pid on record is at most one watchdog interval (~5 min + RandomizedDelaySec) old when line 252 reads it. For `kill -0` to hit a recycled pid, the kernel's cyclic pid allocator must wrap the whole space inside that window: this box has /proc/sys/kernel/pid_max = 4194304, i.e. ~4.19M pid allocations in 300 s (~14k forks/sec sustained). That is fork-bomb territory on a machine that already dies at "pthread_create failed: Resource temporarily unavailable" orders of magnitude below it. Linux allocates pids cyclically from last_pid upward (restarting at RESERVED_PIDS on wrap), so a just-freed pid is not handed out early.

2) The finder's stated route to a durable stale record is wrong. "The old server still owns :3004 so the replacement exits 1" cannot coexist with entering this branch on a healthy owner — if the old server answers /api/artifacts/health the `check` at line 243 passes and the branch is never entered. If the owner is wedged, the recorded pid IS that wedged server (start.sh:587 writes the real python pid via `$!`), so line 253 SIGTERMs the correct target; the next tick finds the dead replacement pid, `kill -0` fails, and it starts cleanly. The loop self-heals rather than accumulating a dead pid. start.sh is also not a source of stale records: it `rm -f "$RUN_DIR/artifact.pid"` on failed startup (start.sh:607) and in its EXIT trap (start.sh:284).

3) The "the artifact path is the one that does not use the identity check" framing is inaccurate. healthcheck.sh's beast-chat path (lines 207-210) is identical by explicit design, and stop.sh's extension loop (`kill "$(cat "$_pf")"`, around line 54) kills a recorded pid with neither a liveness nor an identity check. The comment at healthcheck.sh:246-248 documents the deliberate trade: a pattern kill already destroyed a live measurement run on this box, so short-lived self-written pid records are killed directly. start.sh:_pid_alive/stop.sh:_pid_alive carry the cmdline check because they consult pidfiles that can be arbitrarily old (status reporting, a stack started days ago) — a different lifetime regime from a record rewritten every tick.

Residual worth noting but not a finding: an operator who runs `healthcheck.sh --restart` by hand, fails to start the server, and then leaves the box for weeks of build/eval churn before running it again could in principle span a pid_max wrap (~4.19M spawns). Adding the identity gate would be cheap hardening (it would also have to be written inline, since _pid_alive lives in start.sh/stop.sh and is not sourceable from scripts/lib/), but it is a long-tail residual shared by three other call sites, not a critical defect in the artifact path, and the claimed 5-minute recycle mechanism does not exist.

### agents/artifact_server.py:755
Every ownership guard (D5/D22/R2) authorizes off `Tailscale-User-Login`, an unauthenticated header on the same request that carries the locality token, so the entire owner-only write model is bypassed by adding one header — contradicting docs/BEAST_ARTIFACT.md:286-288 ("forgeable by a process already on the rig … it only ever buys *reads*") and :353 ("Republishing, re-describing, rolling back, re-sharing and deleting are all owner-only").

**Why refuted:** The finder read the code correctly but the scenario's precondition cannot occur as described, and where it can occur the actor already holds strictly greater capability, so nothing is escalated and no documented guarantee is broken.

1) MECHANISM IS AS DESCRIBED (conceded). agents/artifact_server.py:753-757 — with an allowlist, a listed `Tailscale-User-Login` wins the identity slot and `local` is carried alongside it; :680 admits the write verb on `principal.local`; :832 `owner_for` hands that chosen login to the store, and artifact.py:954/990/1010/1024 `_require_owner` compares against it. So token + victim's login = a write as the victim. That part is real.

2) THE PRECONDITION CANNOT OCCUR FOR THE ACTOR NAMED. The scenario's step one is `T=$(cat .run/artifact-local.token)`. That file is minted 0600 and explicitly re-fchmod'd (artifact_server.py:292-293) and owned by the uid running the stack. "kid@example.com" as a second *unix* user on the rig gets EACCES — the scenario dies at step one. The only actors who can read it are the stack uid and root. `ARTIFACT_OPERATORS` entries are tailnet logins, not unix accounts; a second operator who is not the stack uid reaches the server only through `tailscale serve`, carries no token, and is refused every write verb at :680 ("not-local"). That actor can already flip visibility (`sed` on meta.json), roll back (`"current": 1`), reassign ownership, and `rm -rf` the artifact dir — including "irreversibly destroys max's page and every version", which needs no HTTP request at all. The token's own docstring states exactly this scope: "Shared secret proving the caller can read this box's filesystem" (artifact_server.py:280). It is deliberately a locality proof, not a per-operator credential. A guard is not bypassed when the bypass route is a subset of the actor's existing direct access.

4) THE DOCS ARE NOT CONTRADICTED. docs/BEAST_ARTIFACT.md:286-288 reads "…forgeable by a process already on the rig. **That is inside the existing loopback trust model**, and it only ever buys reads — writes need the locality token." The load-bearing guarantee at docs:197-201 ("Write access is loopback-only… Nothing arriving over the tailnet can create, change or remove an artifact — a phone can view and nothing else") holds exactly. docs:353 is a Troubleshooting row explaining the `not your artifact` message, i.e. API semantics among cooperating on-rig identities; those semantics hold for every caller that does not also hold the write credential.

An HTTP header check cannot be a containment boundary against an actor holding a shell as the data's owner, and `publish_artifact`/`list_artifacts` exposing no delete verb was never a sandbox — it is API surface minimization.

6) THE SUGGESTED FIX WOULD BREAK WORKING CODE. Applying this "fix" would make every operator's publishes land on one owner — a genuine regression traded for zero capability removed.

The one residual is cosmetic: the module docstring at :21-23 ("LOCAL principal if it presents the locality token, otherwise whoever Tailscale-User-Login says") reads as token-wins precedence, while :753-757 lets the login name the local principal. The code comments state the real intent explicitly; that is a doc-wording nit, not a defect, and nothing about the test coverage claim changes it — a test that does not cover an unreachable actor is not a vacuous test.

### agents/artifact_server.py:602
The D27 audit-row budget only applies to middleware refusals of an *untrusted* principal, so every router-level 404 from any caller who sends one arbitrary `Tailscale-User-Login` header is written to .run/artifact-audit.jsonl unbudgeted — the unbounded disk-fill primitive D27 exists to close.

**Why refuted:** REFUTED — the finder read the branch correctly but mischaracterized what it is, and their fix closes nothing.

What the code actually does (agents/artifact_server.py):
- L563-575 `audit()` appends one JSON row. L586-636 `_record()` budgets ONLY rows carrying a `denied` key from an untrusted principal (L602); everything else takes the bare `audit(entry)` at L633.
- So yes: a caller with a login header who hits an unmatched path gets a router 404 and one unbudgeted row with `route = request.url.path[:128]` (L584).

Why that is not the D27 primitive:
1. One row per request is the DOCUMENTED design, stated in the module docstring at L37: "audit every request → .run/artifact-audit.jsonl: {ts, login, route, id, n, outcome, ms}". A per-request log grows with requests; that is not a gap between two mechanisms.
2. The 404 branch is not privileged over the success branch. The very same caller (identified, non-operator, default config with no ARTIFACT_OPERATORS) gets 200 from `GET /` (gallery) or `GET /api/artifacts`, and `_record(request, response.status_code, t0)` at L716 writes an equally unbudgeted row through L633. The finder's path therefore grants no capability the caller does not already have; the delta is a constant factor in row size (~180 vs ~110 bytes), not a new primitive. Note also that `entry["login"]` (L591) is untruncated on BOTH branches, so if row size were the concern the 128-byte path cap is not where it lives.
3. D27's own stated scope is narrower than the finder asserts. L149-150: "how many REFUSED requests an unidentified caller may write ... ~89 bytes a row with no bound at all was a disk-fill primitive for anyone who could reach the port." L550 repeats it: refusals are the row an UNIDENTIFIED caller can mint. A caller who sends a login header is, by construction, not the principal D27 budgets — and on the tailnet that header is injected by `tailscale serve`, not chosen by the client; on loopback the only caller who can set it freely is a local process running as the same uid that owns `.run` and could write the directory directly.
4. The decisive point against the proposed fix: an anonymous, zero-credential caller ALREADY mints unbudgeted rows today, and not through a 404. `GET /api/artifacts/health` (L1028-1039) is explicitly exempt from the anonymous deny (L680) and returns 200 to a stranger, and that 200 is recorded unbudgeted at L716→L633. The finder's fix ("budget every row whose outcome is >= 400 and whose principal is not LOCAL") leaves that path completely untouched, so it does not close the alleged disk-fill primitive by a single byte — while it DOES delete audit fidelity that `_trusted` (L800-802) deliberately preserves: a real operator's `not-local`/`oversize` refusals would start being suppressed, which is the R5 blinding failure the current per-reason budget was written to undo.

Sub-scenario (b) is not a defect either: `_trusted` = `p.local or p.operator` by design, an operator is a trusted principal whose own refusals an operator wants in full detail, and an operator can write unbudgeted rows with successful requests anyway (see point 2), so exempting them costs nothing.

Tests: tests/test_artifact_server.py:1255 and :1307 are not vacuous — they monkeypatch DENY_AUDIT_ROWS, assert exact suppressed/written row counts against real file size (`path.stat().st_size == settled`), assert the per-reason isolation R5 added, and pin the shipped constants. They exercise the anonymous middleware deny because that is precisely the threat model the budget claims (L149). They are green for the correct reason, not because a path is unexercised.

Honest residual, well below the claimed severity and NOT the filed finding: the comments at L550 and L149 overstate ("the one audit row an unidentified caller can mint at will") because the anonymous health 200 is also unbudgeted. If someone wants an actual bound on the file, it belongs on the file (size cap or rotation, which L554 consciously rejected) or on an upstream rate limit — never on the 404 branch. Acting on this finding as filed would change working code, degrade operator audit detail, and leave the thing it claims to fix wide open.

### agents/chat_server.py:942
Every unauthenticated request appends a row to `.run/chat-audit.jsonl`, which has no size cap, no rotation and no pre-auth rate limit — the exact amplification the repo's sibling gate (agents/edge.py:582-583) explicitly refuses to allow.

**Why refuted:** The code reading is accurate (denial rows are written pre-auth at chat_server.py:940-943 and 1176-1178; no byte cap, no rotation, rate_check only inside write_gate at 1036/1043), but every claim that makes it a defect fails.

(1) The "sibling gate refuses this exact amplification" pillar is a misread of edge.py. Line 582-583 keeps the denial out of the AUDIT file, then line 584-585 writes it via _log(), which edge.py:388-394 defines as print(..., flush=True) whose own docstring says "stdout -> .run/stack.log in daemon mode". edge.py therefore also appends one line per unauthenticated denial to the same partition; its policy is about keeping the machine-parsed audit trail free of unauthenticated noise, not about unbounded disk growth. The quoted policy does not say what the finder says it says.

(2) There is no amplification. A ~140-byte row costs the attacker a full HTTP round trip through TrustedHostMiddleware, a threadpool hop, json.dumps and an os.open/write/close per request (chat_server.py:900-906). Ratio is at best 1:1. "Hundreds of MB per minute" requires >1.4M req/s; a sync FastAPI handler doing a syscall-heavy append per request realistically caps near 10^3 rps, i.e. ~0.2-0.4 MB/s (~25 GB/day). df shows 395 GB free on /home, so filling it needs roughly two weeks of uninterrupted flooding.
