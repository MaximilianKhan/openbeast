## [42] agents/chat_server.py — medium (certain)
Jobs started through POST /api/chat/sessions have no on-box supervisor — only chat_server's own reaper thread — so a restart of chat_server (routine: healthcheck.sh --restart, driven every 5 min by openbeast-watchdog.timer) permanently orphans them: a clean exit is later filed `lost`, and a /stop already in its SIGTERM->SIGKILL window never escalates. Agent sessions and job.sh-started jobs are NOT affected (the runner finalizes itself; job.sh has its own supervisor process). The finder's mechanism is accurate; this is a design gap in one spawn path, not a code-level bug.

**Reasoning.** Confirmed by reading every piece. An API-spawned job is Popen'd with start_new_session=True (chat_server.py:1622-1633) and its ONLY supervisor is the process-local reaper thread (start_reaper -> reap_session, 700-726) plus the _CHILDREN dict at 621. grep shows no atexit, no signal handler, no on_event/lifespan hook and no startup re-adoption anywhere in chat_server.py; main() (1834) just calls uvicorn.run(create_app()). So on a restart the job is reparented to init, runs to completion, and nothing ever writes a terminal state -> sessions.reconcile (sessions.py:501-518) files it `lost` with "process gone without a terminal event", even for exit 0. The same command under scripts/job.sh is unaffected: _supervise (job.sh:240) is a separate process that outlives the console and writes done/failed/stopped itself. Restarts are routine and automated: scripts/healthcheck.sh:199-231 restarts beast-chat on a failed probe, and scripts/openbeast-watchdog.timer runs `healthcheck.sh --restart` every 5 minutes. The escalation variant is real too — start_escalation's thread (790) is process-local, so a server death in the SIGTERM->SIGKILL window means the SIGKILL never arrives and no terminal state is written. **Minimal fix.** Not a one-liner, and it should not be rushed.
